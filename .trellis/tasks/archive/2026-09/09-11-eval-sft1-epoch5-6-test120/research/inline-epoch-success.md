### Critical distributed failure and waiting design
`stage1/distributed.py:25` initializes NCCL with default timeout; a rank waiting in a single NCCL broadcast/barrier throughout potentially long120 rollout can time out. Do not park nonzero ranks in one long NCCL collective. Use allrank short periodic status collectives while rank0 runs only environment/HF work, with rank0 coordinating at each bounded generation/event or a separate control channel that supports heartbeats and bounded failure detection. Simpler increased explicit timeout must cover full worst-case rollout and is weaker fault diagnosis; do not assume default sufficient. Avoid concurrent NCCL and generation threads unless verified; rank0 can expose a callback in existing scheduler to synchronize status at batch boundaries. All rank0 errors must be serialized and delivered while still in common scope before all ranks unwind; then re-raise on every rank. Catch setup/preprocessing failures as well as rollout failures so peers do not hang. Abrupt rank loss remains launcher failure, not a recoverable Python exception.

### Contracts and validation required
Use original CLI with ordinary validated success-eval configuration overrides; no new executable. Explicit model provenance epoch/step/base/adapter identity plus full resolved eval protocol and generation parameters for each epoch output. Do not pretend in-memory checkpoint path is exported fullHF. Ensure output partial resume only for same weights/epoch/seed/protocol; never reuse older epoch results. Success metric descriptive unless user changes convergence policy. Unit tests should cover RawGeneration EOS/pad evidence, placeholder/image ordering, invalid-action no-op, complete120 denominator, error propagation/mode+RNG restoration, no next epoch before success. Real multi-rank memory/generation/renderer integration required; CPU tests do not prove this.
